# Decisions

| # | Decision | Rationale |
|---|---|---|
| 1 | Separate repo from the Electron app; that app stays the reference and the shareable build | Fallback and Windows coverage stay intact; the native app can diverge in UI without breaking the reference |
| 2 | Swift 6, SwiftUI, minimum macOS 14 | Modern SwiftUI (Observation, MenuBarExtra); owner runs macOS 27 |
| 3 | Hand-written protobuf codec, no SwiftProtobuf | The pedal's messages are small and partly undocumented; the JS implementation is the verified reference and ports one to one; golden tests against recordings replace a schema |
| 4 | `NanoCore` is a Swift package with no CoreBluetooth or UI dependency | Headless tests against recorded packets; transport is a protocol with a `FakePedal` implementation |
| 5 | XcodeGen generates the project from `project.yml`; the `.xcodeproj` is git-ignored | Agent edits and diffs on YAML/Swift instead of `pbxproj` |
| 6 | Bundle id `com.community.nanocortex`, product name "Nano Cortex Editor" | Owner's choice |
| 7 | Not sandboxed, hardened runtime on; local and CI builds ad-hoc signed (release builds: #22) | CoreBluetooth and the Cloud web view work without entitlement work |
| 8 | Upload writes are 500 bytes with the last one padded, exactly like the official app | Proven on the pedal; byte-for-byte golden test in `CaptureUploadTests` |
| 9 | Fixtures are copied from the Electron repo, never raw HCI traces (superseded by #19) | The raw trace carried device addresses and the pedal serial (see that repo's history purge) |
| 10 | `Session.events` carries only unsolicited traffic; a request's reply goes to its caller alone | Otherwise every reply was applied twice (caller + event) and the sync refreshed each block three times. The store applies what it asked for and listens for what the pedal volunteers (footswitch preset changes, dirty flag, tuner, library). |
| 11 | The cab mic/position controls say, in the inspector, that they change the cab slot for every preset | Verified on the pedal 2026-10-08: a type-94 mic/position write lands in the cab slot, survives a preset switch without a save, and every preset using the slot hears it. The preset's own edits (slot choice, level, filters) still need Save. |
| 12 | Accent colours are computed from `AppSettings` (UserDefaults); purple keeps its exact original constants, other accents derive highlight/row/focus by mixing; the Dock icon and header mark recolour `icon.svg`'s LED gradient at runtime, the asset-catalog icon stays teal | A fresh install looks exactly as before; one observable source re-renders every view; no extra icon assets |
| 13 | The metronome starts at Settings' default tempo each launch; overlay tempo changes are session-only; volume, output and sound are shared with Settings | Owner's spec (settings are the defaults); the old last-used `metro.bpm` seeds the default once |
| 14 | The native app's default accent (and Dock icon ring) is blue; the Electron app's stays purple | Anup, 2026-10-09: with both icons following a purple accent he couldn't tell the apps apart in the Dock. Each app's default differs; the user can still pick any accent in Settings. |
| 15 | Metronome bars come from a pure generator (`MetronomePattern.events`); the scheduler places each event relative to the previous one at the current tempo and asks the trainers only at bar boundaries; per-role gains are baked into the buffers; BPM counts the time signature's note value (7/8 at 120 = 120 eighths); swing 100% = triplet feel; subdivision ticks still sound under a muted beat cell, only a gap-muted bar silences them; the tempo trainer returns to its start tempo on Stop | Testable without audio, no drift, the old `player.volume`-per-beat trick applied to everything already queued; off-beat practice needs subs under muted beats |
| 16 | Device settings writes (type 67) carry LED brightness and USB volume together, are sent only after a successful 65/66 read, one at a time with the latest value queued; only those two fields are writable, the rest of 66 is shown read-only | The phone app writes both fields every time, so an unread value would overwrite the pedal's; the other fields' meanings are unverified (PROTOCOL-NOTES §13) |
| 17 | Preset tempo: live writes (145 scope 1) while a control moves, one preset write (scope 0, preceded by a live write with the same value) when it settles, Save commits; field 4 always 0. The metronome's "Follow the preset tempo" is off by default; when on and connected it mirrors the preset tempo and writes its changes back (trainer steps live only) | Same sequence as the official app (trace 2026-10-09), so the pedal never sees an unfamiliar order; a preset write marks the preset edited, which a practice metronome shouldn't do unless asked |
| 18 | Expression records go out in ascending field order (upstream emits its own list order: gain, bass, mid, treble, level, gate, then the FX amounts); an empty bypass record reads as heel-toe 600 ms; heel/toe show capture volume in dB and the rest as % of 0–255 | Canonical protobuf order is what the official app's serializer most likely writes and is identical to upstream for every set in the trace; upstream shows everything as %, but the panel should speak the parameter's units like the inspector. Both unverified on the pedal (PROTOCOL-NOTES §12) |

| 19 | No recordings in the public repo, not even scrubbed: tests inline only the frames they assert (`RecordedFrames.swift`, identifying strings replaced at the same length, capture data synthetic); new recordings go to the git-ignored `recordings/` | Anup, 2026-10-09, before sharing: recordings carry the pedal serial, device ids, users' preset names and third-party Cloud content, and history is forever. Inlined frames keep the golden tests byte for byte |
| 20 | Bundle id stays `com.community.nanocortex` for 1.0 | Changing it would reset existing users' settings, remembered pedal and Cloud login; revisit only if the app is ever notarised under a developer id |
| 21 | Developer tools (Record, Activity, ⌘L, the "Sent: …" status text, hashes, raw device fields) are off by default behind Settings → Advanced, for fresh installs and existing users alike; the dev remote stays build-gated (DEBUG), not switchable. The log file is always written, for everyone, capped at ~2 MB with one rotated `activity.1.log`; Help → Show Log File reveals it | Anup, 2026-10-10: normal users shouldn't meet protocol internals, but a bug report still needs the log, so it is written regardless and bounded so it can't grow forever. Same in the Electron edition |
| 22 | Release builds are signed with the Developer ID Application certificate (team `272K9YT73Z`) and notarised in `release.yml`: the .p12, its password and an App Store Connect API key come from 1Password through a service account (`OP_SERVICE_ACCOUNT_TOKEN`) that can read only the vault `Apple Signing`; the certificate goes into a temporary keychain deleted after the job; `notarytool` authenticates with the API key, the ticket is stapled. Hardened runtime, secure timestamp, no entitlements file. Local and CI builds stay ad-hoc | Anup, 2026-10-10: the download should open without workarounds (right-click → Open no longer bypasses Gatekeeper since macOS 15). One secret in GitHub, everything else in 1Password; an API key needs no Apple ID password or 2FA; fork PRs never see credentials. The app needs no hardened-runtime exception: CoreBluetooth outside the sandbox only needs `NSBluetoothAlwaysUsageDescription`, the metronome only plays (AVAudioEngine output, CoreAudio device listing; no input node, so no `audio-input`), WKWebView needs nothing, and no JIT, unsigned memory, dyld variables, library validation exceptions or Apple Events are used |
| 23 | Updates through **Sparkle 2** (SPM, pinned `exactVersion` in `project.yml`): the standard updater controller and alert (Install Update / Skip This Version / Remind Me Later, release notes, download, verify, relaunch). Feed = an `appcast.xml` **release asset**, read from `releases/latest/download/appcast.xml` (GitHub redirects to the newest non-prerelease Release); `release.yml` makes it with `generate_appcast` (one item: this version's zip on its Release, EdDSA signature, length, the CHANGELOG section as Markdown notes) and checks it against the app's `SUPublicEDKey` (`scripts/verify-appcast.swift`). EdDSA private key: 1Password vault **Apple Signing**, Secure Note "Sparkle Update Signing Key", field `private key` (the release job reads it with the existing service account), plus Anup's login Keychain (`generate_keys --account nano-cortex-editor-mac`). Automatic checks on by default without Sparkle's permission prompt (`SUEnableAutomaticChecks`), daily (`SUScheduledCheckInterval`) plus one background check 5 s after launch (skipped if Sparkle checked within the minute); with `-demo` the updater is never started (UI tests, screenshots); Settings → Advanced switch bound to `automaticallyChecksForUpdates`. Sparkle's helpers are re-signed with the Developer ID in `release.yml` (its ad-hoc signatures would fail notarisation) and the signed app is launched once before zipping. `CFBundleVersion` stays the workflow run number, which Sparkle compares | Anup, 2026-10-20: tell users about new versions and install in one click, no website to host. Sparkle is the standard, EdDSA-verified, works outside the App Store; a release asset keeps everything on GitHub. 1.0.0 has no updater (those users download once by hand). Sparkle's alert keeps its "Automatically download and install updates" checkbox (its default; `SUAllowsAutomaticUpdates` NO would hide it). Ad-hoc *Release* builds no longer launch: with the hardened runtime (#7) library validation refuses the separately signed Sparkle.framework ("different Team IDs"); Debug builds and the Developer ID release are unaffected. Not done: `SUVerifyUpdateBeforeExtraction` / signed feeds (they rule out key rotation through Developer ID signing) |
| 24 | The pedal is remembered (`pedal.identifier`) only once its link is ready: A002/A003 gave C304 + C305 and C305 notifications are on. Only a definitive "not a Nano" (discovery finished without them, on a device that wasn't ready earlier this session) forgets it and skips it for the session; errors, timeouts and dropped links forget nothing. 10 s from link-up (`didConnect`) to ready; no limit on waiting for the pedal to advertise. `didFailToConnect`: 3 tries, then a fresh scan if it was the remembered device, then stop; an automatic reconnect retries a failed setup 3 times. The rules live in `PedalLink.swift` (`GattSetup`, `LinkPolicy`) | Review 2026-10-20, and parity with the Electron fix for its issue #15: remembering on `didConnect` let a wrong device block every later Connect, and missing characteristics hung `connect()`. Forgetting on a transient error would also switch off connect-at-launch (it needs a remembered pedal). Waiting for adverts stays unlimited: after a power-up the pedal only advertises once EXIT + CAPTURE is held, and the card already says "Still trying…" |
| 25 | Metronome sounds per role (Anup, 2026-10-20): Accent, Main beat and Subdivision each play a built-in sound or the user's sample; Settings' single "Click sound" bar became these three rows (seeded from the old `metro.sound`; `metro.sounds` JSON). Soft beats share the main beat's sound and count-in bars use accent and main beat, so there is no fourth row. Picking a built-in sound in a row drops that row's sample (its copy is deleted), like Reset. The picked file's bytes are copied to `Application Support/Nano Cortex Editor/Metronome Sounds/<role>.<ext>` and decoded at each launch (mono by averaging the channels, the engine's 48 kHz, no normalising, the first 2 s with a 5 ms fade; ≤ 5 MiB). A missing or unreadable copy at launch clears that row's sample (log line, one toast) and deletes an unreadable copy. Every sound, built-in or sample, ends where the next event starts (5 ms fade), and each event is two contiguous buffers: the first 10 ms carries the completion callback, the rest follows; the scheduler hands an event to the player once the next one is placed (still at least a beat ahead) | An `AVAudioPlayerNode` plays one buffer at a time: a buffer scheduled while an earlier one sounds interrupts it and the earlier one resumes afterwards, its completion arriving late and out of order (offline render, 2026-10-20). Uncut, a 2 s sample would stutter and the beat indicator would lag by the sample's length; cutting at the next click keeps the onsets and the indicator exactly as before. Clearing a missing sample means one toast, not one every launch; copying the original (not the decoded audio) keeps the user's file as it was |
| 26 | Live pedal sync (Electron #14, from @itsbreaded): NanoCore parses the unsolicited 26/31/64/66/94/99 into `LiveReport` (a missing field is 0; a 26 needs 1:1 and 6:1, else the state is read again); the store applies them at once. The pedal's 115 / field 41 alone drives the unsaved-changes mark, Save and Discard; the local `edited` flag is gone. The prompts (switch, assign, move, scan) also count an edit write queued, in flight or sent < 300 ms ago with no 115 since (`EditGuard`). Reports for a knob being dragged are held, and dropped when the gesture ends (the user's committed value is what the pedal gets) plus 250 ms for older values on their way; a bypass click not yet sent (+ 300 ms) wins over an older 31. Context-free reports (bare 31, 94, an unmapped or unreadable report) make one state read 150 ms after the last, once `Session.isBusy` clears; a preset load cancels it. 31 for the gate's enable slot is read back, as in Electron. FX Amount moves on screen only for Mix / Amount / Transpose → Semitones; the assigned FX blocks that are on are read back at most every 250 ms | Electron staging is the spec; applying in the store keeps NanoCore headless and testable. Dropping a held report rather than applying it after release: applying an older value after the user's final write would show something the pedal no longer has. Waiting for `isBusy` instead of cancelling on "a read started" (Electron) costs at most one redundant read and needs no bookkeeping of who reads the state. Unverified on hardware whether the pedal echoes the app's own writes as 26 (the hold covers it either way) |
| 27 | Monitoring writes (67 field 12 / 13, explicit 0/1) go one at a time through a gate shared with the brightness/USB writes, latest value per switch queued; each accepted write is followed by a 66 read; a switch flips at once, goes back if the pedal refuses (68 status ≠ 1) or the write fails, and Settings says so ("The pedal didn’t take …"). The mutes are read at connect (that first read also gives the brightness/USB sliders the pedal's values); an unasked 66 updates them; a pending switch keeps its value until a read shows it. Tuner close re-arms an input mute like Electron (off, then on 100 ms after that write, unless the user changed it) | A 68 doesn't say which 67 it answers, so two writers could take each other's acks. Electron sends without waiting; one at a time gives the same sequence on the wire for the toggles and the tuner re-arm. The refusal note is ours (Electron only reverts) |
| 28 | Preset reorder by SwiftUI drag and drop: rows carry a private type `com.community.nanocortex.preset-row` (exported in `project.yml`), the drop must name the row the drag started on, so text from elsewhere never moves anything; the source row is cleared by watching the mouse button (SwiftUI reports no cancelled drag). The move asks `prepareForPresetChange()` first (true for now; the audition gate of the parallel Cloud/IR port goes there), then the unsaved-changes prompt (Cancel / Don’t save / Save and reorder), sends 143, ignores 115 until the read-back, reads the list and the state; a failed state read makes the current preset unknown (`PresetKnowledge`), which blocks Save, Save as, Discard and Rename until any state read succeeds. The demo pedal answers 143/144 and moves the current preset and the footswitch slots with their presets, so demo mode can reorder | Electron's behaviour and wording; the order and the current preset are always the pedal's. Footswitch behaviour after a move on the real pedal is unknown, hence the read-back and the manual's "check your footswitch assignments" |
| 29 | Debug builds start the dev remote with the app, not with its window; `/headless` renders the window's content (or Settings) into a window that is never ordered on screen and closes it after the shot | Anup, 2026-10-20: test instances must launch hidden (`open -n -g -j`) and never be activated (no `open -a`, no AppleScript). Such an instance gets no window, so the old window-bound dev remote never came up. Never address a test instance by URL or bundle id (LaunchServices picks the installed app with the same id) |
| 30 | Auditions and transfers (parity with the Electron edition's #14 integration): every action that saves or changes the preset (Save, Save as, the preset switch, Rename, Delete, a footswitch assignment, Discard, the slot scan, an IR delete, and the reorder through `prepareForPresetChange()`) first passes `stopAnyAudition`: nothing playing → go ahead; a start or stop in flight → refused; otherwise the capture preview, then the IR, are stopped and each stop counts only with a 149 that echoes its transaction with status 1, else the action is refused with a message and the audition stays marked as playing. A preset change made on the pedal (footswitch) or a lost link ends the auditions without asking (stops sent best effort). The three streamed messages (13, 15, 150) share one slot in `Session.stream`: a second one is refused (`StreamError.busy`), never queued; the sending task ends with the call (reply, timeout, failed write, lost link or cancel). Keep-alive 91 every 20 s while anything plays, sent as a request that logs the 92; 158, 148 and 82 wait 10 s, streams 20 s. The toolbar's Live Preview follows a pure state machine (`CapturePreviewState`) whose every exit lands in Live or Stop Preview | The pedal may still be playing an audition whose stop it didn't confirm; saving or switching then would store or mix the wrong sound. Refusing (not queueing) a second stream matches Electron and keeps a half-sent message from interleaving. A state machine is the testable form of "the toolbar never sticks" (Electron pushes state on every exit path instead) |
| 31 | Cloud IR bridge: the Send to Nano page script runs in the page world (it reads the IR records React keeps on the list's DOM nodes, as Electron's does) and posts to a `WKScriptMessageHandlerWithReply` in that world; the app accepts a message only from the Cloud web view's main frame, an https `neuraldsp.com` origin, with the web view on `/cloud/profile/impulses` and a UUID product id. The WAV is downloaded with the page's session through `callAsyncJavaScript` (as captures are), capped at 1 MB on the base64 length before decoding, checked (`WAVCheck`), confirmed in the editor, then streamed. Native differences, on purpose: Live Preview is grey while disconnected (like the native Send button; Electron downloads, then refuses); IR: Off/On returns to the cab slot it left; the tab bar's caption gives way when the Cloud buttons need the room at the minimum width; the demo pedal keeps the factory IR list apart from the slot names and starts with one user IR, and checks MD5s, indices and names like the pedal would. The new message types live in `TransferType`, not `MessageType` | Same checks as Electron's main process (sender, host, route, product id, Cloud response); the script and the messages are the site's only way in. The rest keeps each editor's own conventions without changing what goes to the pedal |
| 32 | Preset-row grip (Anup, 2026-10-23): the row under the pointer shows a ⋮⋮ grip (`PresetGrip`: 2 × 3 two-point dots, 6 × 10, 8 points in from the row's right edge, #616161, #ABABAB under the pointer) in a 12-point column that is always reserved; its 20 × 28 target takes the row's right padding. Rows keep the arrow; the open hand only on the grip (`onHover` + `NSCursor` push/pop with a flag, popped when reordering turns off or the grip goes away); the whole row still drags. The drag stays SwiftUI's system drag (#28): the closed hand is set when it starts, and AppKit's drag session then owns the cursor (its drag cursor). The Electron edition moved its row drag to pointer events and keeps the closed hand throughout | The grip is an affordance, not a new mechanism: the move, the private drag type and the UI smoke test's drag stay as they are. A pointer-driven drag here (a `DragGesture` with a hand-drawn drag image and auto-scroll) would match Electron's cursor, at the cost of a second drag implementation verified only on CI; left as a follow-up |
| 33 | Capture descriptions: `CaptureText.description` makes empty, blank and "null" (any case) mean none. Applied where a description is read (18.8, the record's field 5, the library, the Cloud bundle's .json) and in `CaptureRecord.encode`, so "null" is never written to the pedal. Electron: `pro/capture-text.js` | Anup saw "null" in the Electron Info panel on the pedal (that one was Electron's own rendering of a missing paragraph); a "null" from the pedal or Cortex Cloud must not show or round-trip either |

## Deferred ideas
- SwiftProtobuf with hand-written `.proto` files, if the message set grows large.

## Rejected
- Porting before the protocol was hardware-verified (the Electron app did that first, on purpose).
